日志中 Keras 对 Adam 优化器状态发出了变量数量不一致的告警。告警针对训练用优化器状态；本次是推理，模型已成功加载并产生有限预测，因此当前不构成验收阻断，也没有理由因此重装环境或重训模型。它不能证明恢复训练的状态等价。Keras 官方说明模型结构、权重和优化器状态是不同保存内容，见 [保存与加载 API](https://keras.io/api/models/model_saving_apis/model_saving_and_loading/)。HiTE 容器发布标记 3.3.3 与横幅 3.3.2 的差异仍是既有已登记情况，不是本轮新异常。

## 2. hAT 的差异进一步缩小了范围

四个检查点均读取成功，`AUDIT_READY`；443 条匹配全部保存，没有截断。独立复算 59 个位点、236 条计数及所有匹配的交集长度、坐标与重叠比例，并与最初的位点清单逐行核对，均一致。

| 位点组 | 位点数 | v4 初始 GRF 存在完全相同坐标 | v4 后检查点存在完全相同坐标 |
|---|---:|---:|---:|
| 两版共有 | 5 | 5 | 5 |
| 仅 v4 保留 | 2 | 2 | 2 |
| 仅 v3 保留 | 52 | 52 | 0 |
| 优先检查：v3 最终有 DTA 命中、v4 最终未覆盖 | 11 | 11 | 0 |

最后一行是 52 个位点的子集，不应再次累加。52 个 v3 独有位点不只是失去精确边界：在两个后检查点中均没有任何重叠候选。每个位点在初始 GRF 中都有一个边界完全相同、两侧 TSD 长度为 8/8 的候选；其中一个位点还出现于初始 TIRVish 的另一条记录中。

因此，对于这 52 个位置，**初始 GRF 未发现候选**不能解释差异。其跨度最短为 174 bp，也不属于明显低于源码 50 bp 最小输入长度的候选。结合此次完整运行采用 `-s others`，后续重点应放在 CNN 分类及类型相关的 TIR/TSD 筛选。

后检查点合计 679 条记录（TIRVish 17、GRF 662），与原生最终记录总数一致。审计清单中的 7 个保留位点均来自 GRF、类别为 DTA，`sequence_kept_after_overlaps=1`；其坐标和六类整数评分与前次原生 GFF 表逐项一致。

按照审查的 v4.08 实现，`post_CNN` 保存通过 CNN 与结构检查的候选，并附加重叠保留标志；不会仅因该标志为 0 就从检查点删除记录。因此这批记录在检查点中完全不存在，不能只归因于最后的重叠清理。源码依据：[v4.08 CNN 与输出流程](https://raw.githubusercontent.com/KGerhardt/TIR-Learner/v4.08/TIR-Learner4/app/cnn_new.py)。

全基因组原始候选数（TIRVish 577、GRF 139,512）与后检查点数量差异很大，但原始候选包含大量待分类记录。**这些数字不能直接作为假阳性减少比例、召回率或准确率。** 本次 59 个 hAT 位点也是针对性抽样，不代表全部 TE 类型。

## 3. 仍未解决的是哪条筛选条件造成去留

现有后检查点只保存通过者。52 个消失候选的六类预测分数没有出现在反馈中，所以还不能区分：被 CNN 判为 NonTIR、被判为其他类型后未通过对应 TIR 模式、或未通过 TSD 长度/相似度/模式检查。

上一轮发现的 DTA/hAT `TA` 模式条件仍值得检查，但本轮不能将它升级为确定的原因，更不能直接得出“v3 过度注释”或“v4 漏掉的全部是真实 hAT”。v3 作为比较与备用版本，不是真值。详见 [此前的上游规则审计](UPSTREAM_TIR4_AUDIT_2026-11-08.md)。

## 4. 后续执行建议

1. 将新适配器的“有限服务器封装验收”登记为通过，可推进 1.1 发布整理；无需重复安装或为了这次验收重跑整套 EDTA。最终发布仍应审查待提交内容、准确更新验证说明，并检查对应 GitHub 提交的 CI。
2. 保持 v4 CPU 默认、v3 显式备用，不改变评分阈值、TSD 规则或自动合并两版结果。使用新运行配置切换算法，保留旧冻结运行。
3. 若继续追因，执行一次独立的小规模诊断：固定这 59 个精确 GRF 候选，优先审视 11 个重点位点，并以 7 个已保留位点校验一致性。复用原始候选边界、TIR/TSD 长度、相同基因组和已有模型，记录六类原始分数、argmax、TIR 检查、TSD 检查及最后去留；不重跑 GRF、TIRVish、EDTA 或 RepeatMasker，也不改写现有结果。仅用 v3 FASTA 自行拼造不同侧翼不能替代原始候选输入。
4. 原始模型诊断结果可以定位筛选原因，但仍不能单独证明生物学真假。此开放审计与封装发布分别记录，不以恢复 v3 的数量作为发布门槛。

本次复核没有发现需要修复 TEflow 生产代码的阻断问题，也没有启动新的服务器任务或向 GitHub 推送内容。
