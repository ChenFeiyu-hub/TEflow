# TEflow 1.1 多物种开发计划

日期：2026-10-23。状态：**已确定下一轮设计与验收范围；尚未实现多物种生产调度，不是 1.1 发布说明。** 当前公开执行接口仍为 1.0。本文中的 `teflow batch ...` 是拟定接口，不能当作现有命令执行。

本轮测试物种为 Chlamydomonas reinhardtii、Klebsormidium nitens、Marchantia polymorpha、Arabidopsis thaliana 和 Oryza sativa。沿用已有研究中的组装、品系和注释版本，不因本次工程测试统一更换参考。数据准备见 [文件规范](MULTISPECIES_INPUTS_zh.md)，可填写 [五物种清单](../examples/multispecies/inputs.template.json)。

## 1. 下一版的核心决定

采用**一个批次控制器、一个全局阶段 DAG、一个资源池，各物种独立运行目录与科学结果**。物种之间和同一物种内的不同库，共同竞争这个资源池。

延续 Snakemake 管理依赖和任务执行，复用现有工具适配器、产物验证、分支图及租约机制。不会在 Python 外层同时启动五个各自认为拥有全部 CPU/内存的 `teflow run`。软件自身提供批量入口；Slurm 等系统负责节点分配与外层资源隔离，二者不重复安排同一份 CPU 预算。

每个物种保持完整、独立的单物种配置，能够单独审阅、报告与交付。批次只组织计算和汇总，不跨物种合并 TE 库，不改变库选择规则，不强制任何 pCRE/RNA-seq 数据。

第一版支持单个 Linux 节点、固定批次成员、物种内多库并行、失败隔离和显式恢复。跨节点调度、运行中增删物种、自动接管失联控制器、自动推断最优库，不进入首轮验收范围。

## 2. 当前代码核对结果

| 已有实现 | 下一步必须处理的问题 |
|---|---|
| `common.py` 的 `samples` 和 `workflow/Snakefile` 已按样本建立目录 | 多样本目录不等于完成了批量并行；`resources.validate` 明确限制 branch 模式为一个样本 |
| `resource_pool.py` 按 work_root 提供控制器锁、CPU 租约、内存预约和 I/O 槽 | 分别新建五个 work_root 会失去相互协调；必须由批次统一分配 |
| `branches.graph(c)` 描述各库的依赖 | 需要按成员生成图，再合并为互不交叉的全局图；不能让所有物种被迫使用同一组分支 |
| `qc.host_proteins`、工具与资源配置在单物种配置层 | 不能把外部宿主蛋白路径简单复制给所有物种；每成员解析自己的配置 |
| `inputs.derive_cds` 从注释提取完整 CDS，排除显式 TE gene，选最长合格转录本 | 保留原始输入与选择映射；显式 TE 标记不齐全时不能声称已去除所有 TE 蛋白 |
| `launcher.py` 与 `control.py` 支持一次 launch 的协作取消 | 新增批次级和成员级请求，防止取消一个物种变成取消整批 |
| `runtime.py` 冻结运行并验证结果回执 | 新批次必须保留成员身份，不能因另一物种失败或重试而重新计算全部成员 |
| 内存为预约和采样观察；实验性 systemd 后端独立存在 | 继续区分“已预约”“实际观察”“内核硬限制”；过去 B2 通过不等于生产工作流已经接入 cgroup |
| 当前 EDTA 适配器固定 `--species others`，HiTE 根据 taxon_group 设置 plant | 五物种首轮保留科学参数；不能识别到水稻后静默切换 EDTA 参数或引入水稻专用参考 |

相关实现：[resources.py](../src/teflow/resources.py)、[resource_pool.py](../src/teflow/resource_pool.py)、[launcher.py](../src/teflow/launcher.py)、[inputs.py](../src/teflow/inputs.py)、[registry.py](../src/teflow/registry.py)。

## 3. 配置、目录和扩展边界

### 3.1 三种对象分开

1. **输入清单**：物种、品系、组装/注释版本、各文件路径、排除序列及来源。相对路径以清单所在目录为基准。它不是现有 schema 1/2 运行配置。
2. **成员配置**：为每个物种生成一个现有格式的单物种配置，保存自己的分支、宿主蛋白、排除序列、工具参数及 run ID。生成后先供用户检查；不自动启动发现。
3. **批次配置**：成员配置列表、全局预算、共享工作区、失败策略和执行模式。为批次定义独立 schema；不要把批次字段塞进旧配置的未知字段。

新字段以明确的 schema/接口版本引入；当前 1.0 配置和命令保持原语义。库或工具升级只修改分支注册和适配器，不修改队列核心。

推荐的逻辑目录：

```text
project/
  inputs/<sample_id>/                 # 原始输入，只读
  configs/<member_run_id>.json        # 每物种配置
  batches/<batch_id>/
    batch.json
    manifest.json
    attempts/<attempt_id>/            # 控制记录、调度日志、取消请求
    reports/                         # 批次与物种汇总
  work/<member_run_id>/<sample_id>/   # 沿用单物种阶段和产物布局
  results/<member_run_id>/<sample_id>/
  work/.teflow-runtime/               # 同一根目录只有一个活动控制器
```

工作目录与输入目录不得重叠；真实基因组、数据库和运行目录不进入 Git。原始文件允许保留原名，标准化名称只在新准备目录产生，并保留映射。

### 3.2 作业契约

调度层接收通用 `JobSpec`：唯一 job ID、依赖 ID、argv 数组、cwd、资源请求、attempt 目录和归属标签。TE 适配层负责输出校验与科学完成回执。禁止用 shell 字符串拼装用户输入；零退出码不能替代产物完整性判断。

身份至少包含 `batch_id / member_run_id / sample_id / stage / attempt_id`。同一个 `chr1`、FASTA header 或库家族名出现在两个物种内，不构成跨物种同一对象。

批次通过新的执行上下文把全局 pool 与成员阶段关联起来，不能让阶段静默回退到另一份成员私有 pool。上下文须验证批次控制器身份、配置归属和预算；直接伪造环境变量不能绕过原有生产入口检查。

共享只读数据库与环境可去重记录，但不得共享可写 BLAST 索引、工具临时文件或当前目录。若上游工具向输入旁边写索引，就在成员/attempt 的准备目录创建该工具的工作副本或索引。检查与执行使用同一份资源解析结果。

## 4. 调度与内存设计

### 4.1 一级资源池，阶段级申请

同时限制：CPU ID、预约内存、总活动阶段数、重 I/O 槽和重发现槽。轻量 QC、独立库的 RepeatMasker、另一个物种的准备工作，在满足全部条件时可以穿插运行。等待依赖的节点不持有资源；排队本身也不占一个运行槽。

首轮先提供 `max_jobs` 和 `discovery_slots`，不把“最多几个物种”误实现为“最多几个阶段”。不同物种的阶段数量和持续时间不等，按物种计数无法可靠限制资源。公平性先通过固定任务优先级和测试记录检查，不宣称已有动态公平调度或最短总工期保证。

Snakemake 的资源约束和运行时租约必须读取同一份解析后的请求。租约作为最后的保护和归属记录，不应变成占住调度槽的第二层长队列。任一阶段超过全批次预算，应在 plan/check 阶段报错；不能被 scheduler 自动缩减线程后继续运行。

### 4.2 针对目前服务器的初始试跑候选

以下数字是**保守的工程起点，不是由五物种测得的需求或保证**。正式提交前重新读取当前 CPU affinity、可用内存、cgroup/Slurm 上限和磁盘状态；机器上其他任务继续保有其资源。

| 项目 | 初始候选 |
|---|---|
| 批次总线程 | 64 个允许使用的逻辑 CPU；不是声称独占 64 个物理核心 |
| 批次预约内存预算 | 327680 MiB，即 320 GiB |
| 节点可用内存余量 | 65536 MiB，即 64 GiB；若共享节点有其他任务，预算还应下调 |
| 总活动阶段 | 3 |
| 重 I/O 槽 | 2 |
| 重发现槽 | 1；EDTA、TEtrimmer、HELIANO、HiTE 首轮共用该槽 |
| 单个重发现阶段 | 32 线程、131072 MiB 起步；有需求证据时在新运行中调整 |
| 单个 RepeatMasker | 8 线程、32768 MiB 起步 |
| 小型 QC/准备/导出 | 按实际阶段指定；不能假设大基因组导出总在 4 GiB 内 |

先测一项重发现与轻量任务重叠，再决定是否将重发现槽改为 2。禁止直接五个 EDTA 同时开满线程。逻辑 CPU 互不重叠也不等于不同物理核心或独占整台机器；计划输出应展示实际 CPU ID，并报告可用的核/NUMA 拓扑。

新资源结构使用明确的 `memory_mib`/bytes 单位。兼容当前 `mem_mb` 字段时须保留其已有运行时换算并记录适配规则；不能把 MiB、十进制 MB 和 Snakemake 显示文本混用后静默改变预算。

### 4.3 内存压力与长任务

- 继续检查预约总量和实时 MemAvailable；运行在受限 cgroup/Slurm 中时，还要使用实际可见的内存上限和使用量，不能只读整机 503 GiB。
- 新任务进入前，为已运行任务尚未达到的预约量保留余量。共享页重复计算的 RSS 不能当作可靠的“已占用内存信用”；不确定时用保守估计。
- 压力持续出现时暂停新任务发放，记录等待原因、开始时间、最近观测和恢复条件。`queued`/`waiting_memory` 不是 `tool_failed`。
- 排队等待时长与工具执行超时分开。当前默认 600 秒的 admission timeout 不能直接用来终止等待数天的大基因组批次；生产工具超时继续显式配置。
- 运行中超过预约只产生明确告警和停止新任务进入，不冒充硬内存限制。默认不杀其他任务，不按进程名清理，不自动追加内存重试，不依靠 SIGSTOP 释放内存。
- 必须记录 RSS 采样口径、缺失样本、最大采样间隔。不能把各任务在不同时刻的峰值相加，宣称它是批次实际峰值。
- 样本越多，逐阶段反复扫描整个 `/proc` 的成本越高。批次监控应复用同一轮系统采样，记录自身开销；内核 cgroup 观测只在能力确认后使用。
- 自动接管控制器崩溃后仍运行的工具，继续留作独立能力。先可靠报告 `interrupted_review`，核实进程退出后才允许显式恢复。

硬内存限制优先交给已配置的 Slurm allocation；本地可选 cgroup 执行后端需要单独验收真实工具、容器和清理链路。用户选择“必须硬限制”时，能力不可用就应在执行前失败，不能悄悄降为 observe-only。完整登出/重登仍是独立验证，不要求终止同账号的其他会话来完成批量测试。

### 4.4 磁盘与 I/O

启动前、阶段边界和定时监控记录 work/tmp/results 所在文件系统的空间与 inode；同一文件系统不能重复计算可用空间。空间阈值以下暂停新任务，明确标记等待，保留当前日志。

不在短间隔监控中反复对大型目录执行递归 `du`。磁盘预约是估计，工具中间文件受重复结构、候选数量和分支影响，不能根据 FASTA 大小给出固定倍数保证。先通过小规模试跑记录峰值增长，再决定完整五物种批次的工作空间预算。

## 5. 失败、恢复和交付

| 事件 | 预期行为 |
|---|---|
| 输入检查发现问题 | 一次报告所有成员错误；修复或明确缩小本次成员集合后才运行，不静默跳过 |
| 一个物种的发现工具失败 | 阻断其依赖节点，继续其余独立成员/分支，批次最终返回非零及 PARTIAL/FAILED 摘要 |
| 合法零候选 | 依据该工具现有契约报告 valid-empty；不能把缺失文件或崩溃变成零候选成功 |
| 用户取消单个成员 | 写成员/attempt 专属请求，停止其后续节点并清理其自有子进程；其他成员继续 |
| 用户取消全批次 | 停止所有新派发，逐一请求已有作业清理；租约未归零时不能宣称安全结束 |
| 子进程被杀 | 保存原始退出状态；只有内核/cgroup 明确事件才标记 OOM_CONFIRMED，不能仅凭 137 判断 |
| 输入、版本或科学参数改变 | 该成员需要新 run ID；全局工具/代码身份变化不能在旧运行中继续复用 |
| 恢复未改变的失败/中断任务 | 先核对归属、冻结身份和完成产物，只重新执行未完成节点；保留旧 attempt |
| 一个成员完成 | 生成该成员的可用结果与摘要，不等待其他物种全部完成才可查阅 |

批次摘要只汇总状态、时间、资源、库数量、分类覆盖和分支证据，不自动比较不同物种谁“注释更好”。所有坐标和覆盖分母都绑定自己的组装和明确纳入的序列。用户仍逐物种调用显式选择逻辑，不能将 EH、ET 或任意覆盖最高库自动作为全批次最终答案。

## 6. 拟定命令界面

以下仅展示要实现的操作，不是当前可执行命令：

| 拟定命令 | 行为 |
|---|---|
| `teflow batch init` | 读取输入清单与共享安装模板，生成可检查的成员配置和批次配置 |
| `teflow batch plan` | 展示全局 DAG、每成员分支、资源预算与预计需要运行的阶段；不启动工具 |
| `teflow batch check` | 汇总输入格式问题、来源版本、依赖和宿主资源能力 |
| `teflow batch run --dry-run` | 冻结成员/批次身份并验证完整 DAG，不启动基因组发现 |
| `teflow batch run` | 单控制器启动全局 DAG |
| `teflow batch status / logs / report` | 按物种、分支和阶段查询；摘要保留失败与未知值 |
| `teflow batch cancel --sample ID` | 仅取消指定成员；省略 sample 时明确指向整个批次 |
| `teflow batch run --resume` | 在原配置与原软件身份下恢复，不强制解锁，不自动接管活进程 |

计划/检查与执行的边界沿用现有命令习惯。安装依赖、配置数据库、下载文件不作为 batch run 的隐式副作用。

## 7. 实现顺序和通过条件

| 阶段 | 代码落点 | 必须通过的验收 |
|---|---|---|
| M0：本轮规划 | 本文、输入规范、五物种模板 | 必需/可选文件清楚；第二物种确认为 K. nitens；现有执行能力不被误写为已完成 |
| M1：批次清单和预检 | 新 `batch.py` / `batch_cli.py`，复用 `inputs.py` | 重复 ID、混合组装、seqid 错配、错误文件类型一次报告；相对路径解析与配置生成无覆盖 |
| M2：统一调度 | 独立批次 Snakefile、`launcher.py` 扩展、通用 JobSpec 映射 | 不嵌套五个 launcher；CPU 不重叠；内存/I/O/重发现预约不越界；新分支从 registry 自动进入图 |
| M3：运行控制 | 批次控制记录、`control.py` 和资源观测扩展 | 单成员取消不影响另一成员；失败不吞掉；未清理租约禁止恢复；长时间排队可解释 |
| M4：合成与固定库验收 | 新批次单元和真实 Snakemake 集成测试 | 2–5 个微型基因组、不同分支集合、共享 chr 名、不同宿主蛋白、一例失败与一例取消；source 和安装 wheel 都通过 |
| M5：服务器有限真实运行 | 新 run ID 和服务器验收入口 | 先两物种，再五物种；固定库 RM 的串行/并行科学结果可比较；真实容器临时路径和退出归属已核对 |
| M6：1.1 候选版 | 发布文档和结果摘要 | 记录实际测得的吞吐、资源、失败恢复和未覆盖能力；满足接口门槛后才宣布支持多物种生产 |

不新增与实现逐行相同的形式测试；重点覆盖真实跨物种污染、资源重叠、错误成功和恢复重复计算。缺少新物种全基因组数据不阻碍 M1–M4 的开发，但不能据此标记 M5 完成。

## 8. 五物种的测试顺序

1. **输入预检**：五物种一次检查。已有衣藻和拟南芥原始参考可以复用，不需重新下载；仍需确认版本配对与纳入范围。
2. **小型执行验证**：合成数据覆盖调度边界；真实短区域只用于启动/格式/容器检查，不用截短基因组的 TE 发现结果评价算法准确率。
3. **全基因组 E 基线**：每个物种先单独确认 EDTA → 统一 RepeatMasker → 导出可完成。这样区分物种适配问题和并行问题。
4. **固定库并行**：用已经得到的库重放 RM，保持库、参数和纳入序列一致，比较按坐标归一后的注释/屏蔽结果、总工期与资源。拟南芥作为已有参照，衣藻作为第二个较熟悉的输入。
5. **逐步增加物种/分支**：K. nitens、地钱、水稻依次纳入；再依赖各物种单分支结果开启 ET、H、EH、I。HELIANO 与 EDTA 的现有依赖关系保持公开，不称为独立发现对照。
6. **全批次验收**：先 1 个重发现槽，再用实测证据讨论 2 个；不在每物种都尚未单独验证时同时放开所有分支。

资源优化的主要指标是整批 makespan、各阶段等待时间、CPU/内存/I/O 的实际观察、失败后的可恢复性和产物一致性。采用相同线程请求和输入比较串行/并行；若改变线程请求，应独立记为另一个实验。缓存状态、其他用户负载和工具内部随机性影响墙钟时间，应如实记录。

五物种结果用于验证跨输入和跨基因组结构的适用性，不构成普遍准确率或任意超大基因组内存上限证明。藻类的 Unknown 比例和分类分布也不能单独作为工具成功/失败标准。

## 9. 上游依据和可选组件

- Snakemake 已提供阶段资源和调度约束，优先复用；资源是调度声明，不能据此声称具有进程硬内存限制。[资源文档](https://snakemake.readthedocs.io/en/stable/snakefiles/rules.html#resources)
- `shared-local` executor 是可评估的多实例共享资源方案，但其文档说明它不由官方组织维护审阅，且 cgroup 能力不可用时可降级。它不直接替代 TEflow 所需的归属、恢复与“硬限制必需时失败”契约；首轮不同时引入第二个资源账本。[插件说明](https://snakemake.github.io/snakemake-plugin-catalog/plugins/executor/shared-local.html)
- 对 cgroup OOM 证据、memory.current/peak 和边界限制，沿用内核语义并在目标主机验证。[cgroup v2 文档](https://docs.kernel.org/admin-guide/cgroup-v2.html)

这些是设计依据，不是本项目已完成相应生产后端验收的证据。源码、上传包和反馈不增加人工 SHA-256 步骤；下载的外部数据/工具仍可核对发布方校验信息，内部科学身份机制继续保留。
